HW 4: Unity No-Code Toolkit

CS 480 · Interactive XR Documentaries · Fall 2026

Project Overview

For this assignment, I built a small toolkit of reusable Unity components that let a designer create interactions through the Inspector instead of writing a new C# script for every event. The toolkit includes a trigger action, a timer, a collision action, and a sequence action. I also explored Unity's built-in XR Grab Interactable to see how an existing component exposes useful interactions through Inspector events.

The goal is to make common interaction logic easier for non-programmers to configure. A designer can choose what happens when an object enters an area, when time runs out, when two objects collide, or when a sequence reaches each step, simply by connecting events to public methods in the Unity Inspector.

Toolkit Scripts

These are the four reusable components used in this assignment. The links below point to the C# files in the scripts folder. Keep the files in that folder or update the links if you organize the archive differently.

  • OnTriggerAction.cs — responds to tagged objects entering or exiting a trigger.
  • TimedAction.cs — runs and repeats an event after a countdown.
  • CollideAction.cs — responds to physical collisions with tagged objects.
  • SequenceAction.cs — runs a timed sequence of UnityEvents.

Reflection: Key Takeaways

One takeaway for me is that a small amount of reusable scripts allows for a great deal of customization. With just four scripts, virtually all time-based and collision/trigger based events and sequences can be configured through the inspector interface. I'm sure that other events and features can also be generalized easily, so maybe we can add to our toolkit in the future if needed.

A second takeaway is that timing and order matter in XR interactions. A sequence can make an interaction feel intentional by spacing out text, sound, and environmental changes. At the same time, each delay and event connection needs to be easy to understand so another designer can adjust it safely.

A third takeaway is that documentation is essential when working with non-engineers. Compared to other CS homeworks, which required minimal documentation as they would be viewed and graded by a CS instructor, the toolkit requires much more guidance built in. Designers are not only unfamilliar with programming, but also with the relatively complex Unity inspector interface. It's important that they have guidance in a medium that's familiar to them.

Connection to our Project

The toolkit enables designers to participate in the implementation of their vision. Rather than having to communicate their vision to the programmers in the group and playing a game of telephone, they now can seamlessly implement their ideas, themselves in any way they chose. Since all of our teammates parttake in the design of our projects, it is important that we also all can contribute to the implementation. Of course, more complex and non-standard interactions will still require custom scripts, but the toolkit is highly extensible and we can always add new scripts for our collaborators to use.

Challenges and Documentation Testing

One challenge in this kind of toolkit is making sure the components work together rather than only working in isolation. Tags, Collider settings, Rigidbody requirements, and UnityEvent references all need to be configured correctly. A small setup mistake can make an interaction appear broken even when the script itself is correct.

In testing with my non-programmer roommate, I found that it is difficult to generalize the documentation for the toolkit to clarify the breadth of configurations it enables. My roommate kept asking questions about what could be used where and what could be used as variables in the scripts. I realized that I needed to clarify the documentation to explain that the scripts are designed to be flexible and work with any object that meets the requirements, rather than being limited to specific objects or scenarios.
